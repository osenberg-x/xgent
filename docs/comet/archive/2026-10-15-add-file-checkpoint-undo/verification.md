## Risks and skipped work

- Coverage overpromise in user-facing wording: run_command side effects and plugin writes are not undoable, and I confirmed plugins bypass the mechanism entirely (xgent_plugin/src/host_state.rs:64-79 uses plain tokio::fs::write, never the executor). The limit IS documented (doc/dev-tutorial.md:645) but is NOT disclosed to the user anywhere: no undo-* key mentions it, so the palette label 'Undo last turn's file changes' and undo-done imply full coverage. The brief's Scope claims the limit 'is stated in the tool's own notice' and the handoff repeats that; both are refuted by the catalogues. Not an acceptance-item failure (A10 only demands keys exist), but the claim should be corrected or a notice key added.
- Dead public API left behind: crates/xgent_tools/src/atomic.rs:25 still exports pub const BACKUP_SUFFIX with zero consumers anywhere in the repo (verified by grep); the stated reason for keeping it, 'to recognise historical files', is not implemented by any code. Either use it or delete it.
- command_palette.rs:99-105 swallows the registration error with .ok(). CommandRegistry::try_register returns Err with an id-conflict message (xui/src/command_palette.rs:54-60), and the other five commands in the same function use registry.register directly. A duplicate id would make the undo command silently vanish from the palette with no log and no failing test - precisely the silent-loss class this round's method exists to catch. Should at least tracing::warn on Err.
- checkpoint.rs:329-334 redundant assignment: the UndoReport struct literal already sets turn: Some(key), then line 334 assigns report.turn = Some(key) again. Harmless but noise; also executor.rs's new test ends with 'let _ = EntryKind::Modified;' kept only to silence an unused-import warning.
- Restore does not re-validate the manifest path against the project root: restore_entry builds the target as project_root.join(&entry.path) (checkpoint.rs:363) without resolve_in_project or a relative check. Paths recorded by the store are always strip_prefix-relative (relative(), checkpoint.rs:630-644) and the recording side is tested (paths_outside_the_project_are_ignored), so this is not reachable through the product's own writes - but a hand-edited or corrupt manifest with an absolute path or '..' segment would let undo overwrite or delete outside the project, weakening the brief invariant 'every path goes through resolve_in_project' to the recording side only. No test covers a hostile manifest.
- Ownership is decided by content equality alone, with two blind spots I confirmed from source: FNV-1a 64 is documented in-repo as not collision-resistant (checkpoint.rs:651-654), and a user file whose bytes happen to equal what the agent wrote is treated as the agent's and can be deleted or reverted. Also finalize_after_write re-reads the file after execute returns, so a user edit landing inside that window is recorded as the agent's own content and would later be overwritten. Narrow, but it is the honest boundary of the hash approach.
- A write that fails is recorded but NOT reachable by undo: run_tool only calls finalize_after_write when the result is not is_error, so the entry keeps post_hash None and restore_entry skips it as Unverified. The pre-state blob is durable, yet the stated purpose of snapshot-before-write (recovering a file whose write failed midway) is therefore not delivered, and no test covers this case. It is reported honestly, but deserves either a spec sentence or a rule allowing restore when post_hash is absent and the current bytes still equal pre_hash.
- Manifest read-modify-write is not serialised by the store's Mutex: snapshot_before_write, finalize_after_write and record_entry lock only to read the current turn key, then load/write the manifest outside the lock (checkpoint.rs:219-288). Correctness rests on write tools being Concurrency::Exclusive, which write_file.rs and edit_file.rs both are; a future write tool that declares targets but runs Shared could lose entries with no test catching it.
- Untested halves of A8 and A9 that I could only confirm by reading: no test inspects the blobs directory, so blob eviction on retention is unasserted; and no test asserts the absence of *-xgent-tmp leftovers after undo.
- UndoPlugin's three systems are never executed by any test (no UI integration harness builds them, only xgent_app does), so their resource requirements (Res<AgentBridge>, Res<Conversation>, Res<Localizer>, Res<ChatPanelEntities>, Res<Theme>) are verified only by reading provisioning sites (main.rs plus chat_panel.rs:99 and xgent_agent/src/lib.rs:75 init_resource). A missing resource would surface as a runtime panic on the first undo, not as a red test.
- Dangling and inconsistent doc references for the same spec: doc/dev-tutorial.md's F-03 row points at docs/comet/specs/file-checkpoint-undo/spec.md while doc/notes/agent-gap-disposition.md section 8 points at docs/comet/specs/file-checkpoints/spec.md; neither path exists today (the real file is docs/comet/changes/add-file-checkpoint-undo/specs/file-checkpoint-undo/spec.md). One of the two names should be fixed before Archive promotes the spec.
- Unchanged pre-existing limits that are out of this change's scope but still true for users: retention is fixed at 20 turns with no config key, there is no redo, no history UI, no whole-session revert, existing *.xgent-bak files in user projects are not cleaned up, and the app still does not ensure the user's project gitignores .xgent/. The builder's incidental finding that EditorIoRuntime.handle is never injected by xgent_app is corroborated by the code comments in undo.rs:83-85 and deserves its own change.
