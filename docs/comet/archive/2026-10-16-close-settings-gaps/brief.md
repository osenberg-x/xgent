# Outcome

The settings panel (`crates/xgent_ui/src/settings_panel.rs`) is the product's only configuration screen and it exposes four provider fields. Everything else the last three changes added — `[tool_policy]` (the `AGENTS.md` §5.4 safety knob), `[agent] max_parallel_tools`/`retrieval_max_tokens`/`max_events_per_frame`, `[tools] confirm_timeout_secs`/`command_timeout_secs`/`command_max_output_bytes`, `[context]`'s five retrieval limits, and the provider limits `context_window`/`max_output_tokens`/`first_event_timeout_secs` — can only be changed by hand-editing TOML. Two of those paths are worse than missing: the daemon answers `config scope=project` with an explicit rejection (`crates/xgent_daemon/src/session.rs:206-215,237-246`), so project-scope keys are unreachable over IPC by design, and `providers.<id>.context_window` and friends are not in the daemon's key whitelist (`crates/xgent_daemon/src/config_store.rs:131-145`), so a global write returns `未知配置 key`. The panel is also write-only: `spawn_panel` never prefills, so reopening shows four blank boxes, and `handle_save_button` sets `open = false` even when nothing was written (`settings_panel.rs:509-518`).

After this change, opening the panel shows the real current value of every field it exposes — including the "unset means the built-in default" case, which is displayed as the effective number with the fact that it is not set — and the user can change: tool policy per registered tool as a three-state row (auto / ask / deny) that reflects `resolve_policy` precedence rather than two raw string lists; the `[agent]`, `[tools]`, `[context]` numeric limits; `context_window` and the provider advanced limits; and the language preference. Saving writes through the daemon (global keys via the existing path, project keys via a newly implemented `scope=project` that carries the project root) and takes effect at the next point of use — next tool call, next confirmation, next command, next retrieval, next message — with no restart, because each consumer reads its value through a shared handle the same way `retry_config` and `loop_bounds` already do. A field that fails validation or fails to write is reported per key, the panel stays open, and the keys that did land are named. A second window on the same project sees the same values and the same live behaviour, through the `config.changed` notification that already exists.

- `doc/notes/agent-gap-disposition.md` §七/§八/§九 "遗留与下一步" — names this gap three times as the next step, each time because a newly shipped key became unreachable (`max_parallel_tools`, checkpoint retention, 14 new keys).

## In scope

- **Reachability**: implement `scope=project` read and write in the daemon behind the existing `ConfigCoordinator` shape (a per-project-root authoritative copy, loaded on demand, saved atomically through `ProjectConfigStore`), carrying the project root in `ConfigReadRequest`/`ConfigWriteRequest` and in the `ConfigChanged` notification. Add the whitelisted global provider fields `context_window`, `model_context_windows` (read), `max_output_tokens`, `first_event_timeout_secs`.
- **Key grammar for project scope**: `tool_policy.approved`, `tool_policy.denied`, `agent.retrieval_max_tokens`, `agent.max_parallel_tools`, `agent.max_events_per_frame`, `tools.confirm_timeout_secs`, `tools.command_timeout_secs`, `tools.command_max_output_bytes`, `context.tree_max_depth`, `context.tree_max_entries`, `context.rg_timeout_secs`, `context.max_search_files`, `context.max_keywords`.
- **Read model**: `xgent_app` populates `GlobalConfigRes`/`ProjectConfigRes` from the daemon when the panel is opened and keeps them in sync after its own writes and after `config.changed`; the panel binds its fields to those resources.
- **Panel sections**: provider (existing four fields plus the advanced limits), tool policy (one three-state row per tool registered in the `ToolExecutor`, builtins and plugin proxies alike), agent limits, tool limits, retrieval limits, language. Numeric fields show the effective value when unset and accept empty/`0` as "unset".
- **Validation and honest reporting**: per-field parse/validation before any write; batch write of only the dirty keys; on failure, name the keys that were written and the key that failed with the daemon's reason; the panel does not close on failure.
- **Live apply**: `tool_policy` (via a shared handle in `ToolCtx`), `[agent]` values plus `context_window` (shared run-settings handle on the bridge, read per message), `[tools]` values (shared `ToolParams` in the executor and `RunCommand`), `[context]` values (shared `RetrievalLimits` in `OnDemandProvider`), plus the daemon's existing provider-pool invalidation for provider limits. One apply function serves both a local write and a remote `config.changed`.
- **i18n**: every new user-visible string, including labels, hints, error text and list punctuation, as keys in both `zh-CN` and `en-US` bundles, added to the missing-key guard test.
- `doc/dev-tutorial.md` and `doc/notes/agent-gap-disposition.md` §十.

## Out of scope but adjacent

- Theme selection: `xgent_ui::theme` ships one dark preset (`theme.rs:202`, "MVP 仅暗色预设") and `preferences.theme` still has no consumer — a picker with nothing to pick is R3-14, a separate change.
- `plugin.enabled` / `plugin.auto_update` / `plugin.auto_install` / `[plugin_settings]` UI: `PluginHost::update_plugin_settings` (`xgent_plugin/src/host.rs:96-103`) has no caller, so a switch there would not hot-apply; needs its own plugin-reload work.
- Free-form map editing for `extra_headers` and `model_context_windows` (beyond reading the resolved value), and per-model window overrides UI.
- `context_strategy` selection — `repo_map`/`vector`/`hybrid` are still stubs (R3-2), and choosing one currently exits the process (`main.rs:128`).
- `provider_override`, and `model_override` in particular, which no code reads (`project.rs:18`) — a dead key must not get UI.
- `api_key` storage in the OS keychain (D-02) — the panel keeps using the existing field and the existing `keychain::resolve_api_key` precedence.
- Conflict resolution between two windows editing the same project config at once: last write wins, as today; only the notification keeps the display honest.
- Any change to what the numbers mean: this change moves values, not semantics.

# Non-goals

- Not a restart-free guarantee for every key in the workspace: the four groups named in Scope apply live; anything outside them keeps its current startup-time reading.
- Not a general settings framework, form-validation DSL, or preference-search. No new widget components in `xui` beyond what the panel needs from official `bevy_ui_widgets` and `xgent_ui::kit`.
- Not a second config writer: the daemon stays the only process that writes `~/.xgent/agent/config.toml` or a project's `.xgent/config.toml`.
- Not light theme, plugin management UI, or the `model_override` dead key.
- Not a benchmark of daemon round-trips; save latency is asserted only as "the value read back equals the value written".

# Acceptance examples

- **A1**: opening the panel with a config that sets `providers.openai.api_base = "https://example.test/v1"` and `[agent] max_parallel_tools = 2`, and a config that sets nothing, each render those actual values; an unset numeric field shows the built-in effective default (`4` for `max_parallel_tools`) and states that it is not set. This holds for the existing four provider fields too — reopening the panel no longer shows blanks.
- **A2**: the tool-policy row for `read_file` under default configuration shows 询问 (`NeedsConfirmation`); after saving 自动执行 it shows 自动执行, `[tool_policy] approved = ["read_file"]` is on disk in `.xgent/config.toml`, and `model_context`/`resolve_policy` for a `Read` tool with that policy answers `Approved`. `editor.open_file` (`UiOnly`) shows 自动执行 without any configuration (R3-15's finding must stay visible to the user).
- **A3**: setting `run_command` to 拒绝 writes `tool_policy.denied`, and the next `ToolExecutor::execute` for it returns a `denied` result without touching the confirmation channel.
- **A4**: setting `run_command` to 自动执行 does **not** silence confirmation for a dangerous command: `resolve_policy("run_command", Exec, {"command":"rm -rf /"}, …)` still answers `NeedsConfirmation` while a plain command answers `Approved` (the dynamic-escalation branch of `security.rs:38-45` must survive the UI).
- **A5**: the UI never writes the same tool id into both `approved` and `denied`: choosing a third state removes the id from the other list, so a tool that was 自动执行 and becomes 拒绝 lands only in `denied`.
- **A6**: changing `max_parallel_tools` to `1` at runtime makes the next tool-call batch observe a maximum of one call in flight, and changing `retrieval_max_tokens` to `500` makes the next retrieval request carry `max_tokens: 500`, both without rebuilding the bridge or restarting; writing `0` instead means "unset" and resolves back to `4`/`8000`, never to unlimited (the R3-17 trap).
- **A7**: changing `confirm_timeout_secs` to `1` at runtime makes the *next* confirmation request expire in about a second instead of 300; changing `command_timeout_secs` to `1` makes the *next* `run_command` kill a slow command at about a second instead of 60.
- **A8**: changing `context.tree_max_depth` to `1` at runtime makes the next directory-tree summary shorter than the default depth-4 summary, and `context.max_keywords` to `2` makes the next keyword extraction keep at most 2 keywords in order.
- **A9**: a field holding `abc`, a value above its documented cap, and a field left empty are handled distinctly: the first two produce a per-field i18n'd error and no write at all; the empty one is a valid "unset" that writes `0`. If the daemon rejects one key mid-batch, the report names the keys already written and the failed key with its reason, and the panel stays open with the failed value still visible.
- **A10**: `config.read`/`config.write` with `scope=project` and a project root return and persist `[tool_policy]`/`[agent]`/`[tools]`/`[context]` values in `<project>/.xgent/config.toml`, reject an unknown key with `未知配置 key` exactly as the global path does, and broadcast `config.changed` only to clients subscribed to that project (a second window on a different project is not notified). `scope=project` without a resolvable root is rejected rather than silently treated as global.
- **A11**: writing `providers.openai.context_window = 32000` over IPC succeeds (it is no longer `未知配置 key`), invalidates the provider pool as other `providers.*` writes do, and the next conversation's compaction decision uses the new window; `max_output_tokens` and `first_event_timeout_secs` round-trip through the daemon and reach the provider built for the next request.
- **A12**: a second UI window on the same project, without any interaction of its own, updates its displayed values and its live tool policy after the first window saves — driven by `config.changed`; `GlobalConfigRes`/`ProjectConfigRes` reflect the new state.
- **A13**: every new user-visible string exists in both `crates/xgent_settings/locales/zh-CN/main.ftl` and `.../en-US/main.ftl`, punctuation included; deleting one key from `en-US` fails the guard test, and the English panel renders no Chinese punctuation.
- **A14**: `cargo test -p xgent_settings_core --lib`, `-p xgent_daemon --lib`, `-p xgent_tools --lib`, `-p xgent_context --lib`, `-p xgent_agent --lib`, `-p xgent_ui --lib`, `cargo test -p xgent_ui --test settings_input_focus`, `cargo check --workspace --all-targets` and `cargo fmt -p <crate> -- --check` for every touched crate pass, with all pre-existing tests untouched in behaviour. The GUI-only paths (actual mouse interaction with the new rows) are recorded as such rather than claimed.

# Constraints and invariants

- The daemon remains the single writer of both config files; `xgent_ui` never touches the filesystem for configuration and talks to `xgent_app` only through ECS messages (§5.2), which is what `config_bridge.rs` already does.
- Semantics of existing keys are frozen: `0`/absent = unset = built-in default (`project.rs:94-117`, `global.rs:125-132`), `max_parallel_tools = 0` means `4` and not unlimited (`project.rs:315-331`), `api_key` still prefers the keychain (`keychain.rs:166`).
- `resolve_policy`'s precedence and dynamic escalation are not weakened by any UI state; adding a UI must not make a dangerous command quieter than it is today.
- Default configuration behaviour is unchanged: with an empty `[tool_policy]`, every non-`UiOnly` tool still asks, and the panel is the only thing new on screen.
- `xui` stays free of `xgent_*` dependencies (§4); the panel lives in `xgent_ui`.
- No new external dependency. Library code avoids `unwrap()`/`expect()` (§5.7). Comments, docs and commit messages in Chinese; user-visible strings only through i18n (§5.8, NF-05).
- Existing IPC wire formats stay readable by old clients: the new request/notification fields are `#[serde(default)]` options, and a `scope=global` request without a project root behaves exactly as before.

# Decisions

- **D1 — project-scope writes go through the daemon**, not through `ProjectConfigStore` called from the UI process. Reason: the daemon is the only writer today and the only place that can broadcast `config.changed` to peers; two windows on one project writing `.xgent/config.toml` directly would silently clobber each other. The protocol already reserves `ConfigScope::Project`, so this fills a declared hole rather than inventing a channel. Rejected alternative: UI-side direct write (cheaper, but breaks the single-writer rule and peer sync).
- **D2 — the project root travels in the request** (`ConfigReadRequest`/`ConfigWriteRequest`) instead of being inferred from the client's `fs.watch` subscription. Reason: a client may subscribe to several roots, and inferring "the first one" would write to a project the user is not looking at. No subscribed root is an error, not a fallback.
- **D3 — tool policy is a three-state row per tool, not two editable string lists.** Reason: `denied` outranks `approved` in `resolve_policy`, so two lists let the user write a combination whose answer is the opposite of what the second list says; a row makes the resolved answer the only thing visible. Rows come from the `ToolExecutor`'s registered tools, so plugin proxy tools appear with the same mechanism as builtins.
- **D4 — live apply uses one shared handle per consumer group** (`Arc<RwLock<…>>` for tool policy, run settings on the bridge, `ToolParams` in the executor, `RetrievalLimits` in the provider), following `retry_config`/`loop_bounds` rather than introducing a new reactive layer. Reason: those handles are already the codebase's answer to "value changes after construction", each read point is per-call or per-message, and the effect boundary is describable per group. `Default`-typed `Arc<RwLock<T>>` keeps the ~14 test `ToolCtx` construction sites compiling unchanged.
- **D5 — one apply function serves local writes and remote notifications.** Reason: the two must produce identical runtime state; a divergence would mean a second window's agent behaves differently from the window that changed the setting.
- **D6 — batch save of dirty keys with per-key reporting.** Reason: the panel currently closes even when it wrote nothing; a save that partially succeeded must say so. Rejected alternatives: save-per-field-change (many IPC round-trips, and no single validation point) and "restart to apply" labels for keys that can apply live.
- **D7 — theme and plugin keys stay out.** Reason: with one theme preset a selector is a lie, and `update_plugin_settings` has no caller so a switch would not apply — both would ship unreachable state rather than close a gap.

# Verification expectations

- Behaviour tests, not grep-only claims, prove each live-apply path: the A6/A7/A8 items must observe the *new* value being read at the point of use (same standard as R3-17's MU-series and R3-15's AP-series).
- Daemon tests must cover the real disk path for project scope — the existing `config_store.rs` tests all use `with_config` and never write a file, and their module comment claims 持久化; at least one test must assert the TOML on disk and the `ConfigChanged` scope/root.
- Panel display is asserted with the headless Bevy app harness already used by `crates/xgent_ui/tests/settings_input_focus.rs`; anything that needs a real pointer or a real second process is reported as unverified rather than inferred.
- Full mutation-style discrimination over the new judgements (policy row → resolved state, unset-vs-zero, per-key error reporting, project-scope routing, each live-apply handle), choosing the test target by where the assertion lives, not by which crate owns the mutated file.
- Machine constraint: `cargo clippy --workspace` and `cargo test --workspace` link the whole Bevy graph and took 10+ minutes on this box (ledger §七); the check plan must state which of them run and must not assert a check that was not executed.
