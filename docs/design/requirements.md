## 1. 项目定位与目标

### 1.1 定位

**XGent 是一个面向个人开发者日常编码的桌面端 AI Code Agent 工具，基于 Bevy 游戏引擎构建。** 它以一个完整可用的产品为目标，让开发者在本地项目中获得 AI 辅助编码、代码理解、自动化操作的能力，同时通过轻量创意的视觉与陪伴体验，区别于同类工具。

### 1.2 核心价值主张（四大支柱）

> 2026-10-30 起，README 的四大支柱是主线依据，不再只是愿景稿。每个支柱都有需求编号与阶段。

| 支柱 | 核心命题 | 需求落点 | 阶段 |
|:---|:---|:---|:---|
| **3D 可视化** | 代码不再是平面的文本列表，而是可探索的空间 | F-16 3D 代码宇宙（首页） | MVP-2 |
| **时空回溯** | 每次操作都是可回溯的时间锚点 | F-20 时空回溯 | P1 |
| **数据驱动 UI** | UI 即 Agent 状态的实时投影 | §3「数据驱动」原则 + 架构 §5.2 的 ECS 事件/消息契约 | 已交付（持续） |
| **沉浸式协作** | 人与 AI 在同一空间中工作 | F-22 多 Agent 编排与沉浸式协作 | P2 |

跨支柱底线：

- **实用优先**：任何创意/视觉服务于实用性；3D 是默认首页，但 2D 始终可用（见 §3）。
- **可扩展**：TUI / Web / 自定义工具在架构上预留，不因当前不实现而阻塞未来扩展。
- **创意陪伴**：F-15 桌面宠物作为情感化补充，独立开关，不影响四大支柱。

### 1.3 产品形态

- **MVP-2 目标形态（首期已交付，收尾集成验收）**：跨平台桌面 GUI（Windows / macOS / Linux），**默认 3D 首页**：
  - 主区是 3D 代码宇宙；打开文件或终端时主区让位，Esc 回到宇宙；
  - 对话常驻右侧栏，写代码时仍可见；
  - 2D 模式始终可用：用户可在偏好里关掉 3D 首页，退回纯 2D 面板；所有 3D 操作都有 2D 入口。
- **MVP-1（已交付）**：2D agent IDE——对话主区 + 编辑器/终端侧区。
- **预留形态**：
  - TUI 前端（未来作为同一套核心的另一套 UI 前端实现）。
  - Web 端（架构层面留好抽象接口，当前不实现）。

## 2. 目标用户与使用场景

### 2.1 目标用户

个人开发者，在本地编码项目中希望借助 AI 完成日常编码、代码理解、自动化操作的开发者。

### 2.2 使用场景

- 在本地代码项目中与 AI 多轮对话，请求修改、解释、生成代码。
- 让 AI 通过工具读写文件、搜索代码、运行命令，并经用户确认后执行高危操作。
- 同时并行处理多个项目（多开窗口）。
- 在编码陪伴中获得轻量的情感化反馈（桌面宠物）。
- 在 3D 宇宙中浏览项目结构，点星球直接打开文件；点开后主区让位给编辑器，Esc 回到宇宙。

## 3. 设计原则

| 原则 | 含义 |
|:---|:---|
| **实用优先** | 任何创意/视觉服务于实用性，不为酷炫牺牲核心流程效率；3D 与 2D 可切换，核心编辑流不被 3D 动画阻塞。 |
| **数据驱动** | UI 是 Agent 状态的实时投影；子系统经抽象事件/消息通信，可推理、可测试、可回放。 |
| **可扩展** | TUI / Web / 自定义工具在架构上预留，但不引入当前不用的复杂度。 |
| **轻量** | 多开、共享运行时资源、低占用；不因游戏引擎背景而忽视资源效率。 |
| **3D 主线** | 3D 不再是可选插件层：它进入 MVP-2，是默认首页，受 G7 性能门与 2D fallback 约束（§4.2）。 |
| **可玩性优先** | 操作感来自反馈而非飞行物理：悬停/选中/相机过渡有明确动效，时间回溯有拖拽手势；每一次“好玩”都必须有对应键盘路径。首期用轨道相机，自由飞行/惯性不在 MVP-2（OQ-13）。 |
| **渐进式沉浸** | 3D 是默认首页，但用户可从纯 2D 模式起步或随时切回；不强制动画。 |
| **跨平台** | 桌面端 Windows/macOS/Linux 同步支持；为未来 Web 端留接口。 |

### 4.2 3D 首页（MVP-2，当前主线）

> 2026-10-30 决策：3D 从 P2 提升为 MVP-2；第一里程碑只交付「3D 首页」的最低可用闭环，不一次铺完 S0~S4。设计细节见 `docs/design/ui-v8-3d-viewport.md`。

| 编号 | 功能 | 描述 | 优先级 |
|:---|:---|:---|:---|
| F-16 | 3D 代码宇宙（首页） | 默认主视图：L1 文件/目录图 + 目录簇、轨道相机、悬停高亮、点击选中、双击/Enter 打开文件、Esc 回宇宙；对话常驻右栏；2D fallback | MVP-2 |

**数据源**：`xgent_spatial` 在 S0 的 crate 图之上扩展 **L1 文件/目录图**——文件树聚合为 Module/File 节点 + 目录簇，所有项目通用；有 `Cargo.toml` 时叠加 crate 依赖边。符号/import/调用边留给 F-21。节点上限与聚合策略受 G7 约束。

**布局**：3D 占 `Slot::Center`；打开文件/终端时主区让位，Esc 回宇宙；对话从 Center 降到右侧栏并常驻。编辑器/终端不再是侧区页签，而是主区接管者。

**交互形态**：轨道相机（拖拽改 yaw/pitch、滚轮缩放、无惯性）；单击选中、双击/Enter 打开文件；Esc 回宇宙。不做自由飞行/惯性——默认首页不能与编辑器争键盘（OQ-13）。所有首期操作（选中/打开/返回/相机）都有键盘路径；2D/3D 可随时切换，不重启。

**第一里程碑验收**：

1. **G7 性能 spike（先做）**：2k 实例化节点 + 离屏纹理在默认 1280×800 窗口 / 集显 60fps（另记 1080p 压力值）；测试机固定为本机 Windows（优先集显；若只有独显则记录并标注）；不过则降到 800 节点/关特效，必须 800@60fps；再不过则 3D 首页回退 2D。G7 未通过前不动布局。
2. **S1 + 点击打开**：渲染、轨道相机、悬停高亮、点击选中、双击/Enter 打开文件、Esc 回宇宙；2k 节点 60fps；所有首期操作都有键盘路径。
3. **L1 数据**：任意项目打开都有宇宙；文件树扫描忽略 `.gitignore`/`target`/`node_modules`；无 `Cargo.toml` 时仍有目录/文件节点，只是没有 crate 依赖边。
4. **布局反转**：对话右栏常驻；编辑器/终端接管主区；2D/3D 可随时切换、不重启；关掉 3D 后 MVP-1 的全部功能可用。

**本期不做**：完整 S2（键盘遍历、搜索飞行、2D↔3D 联动）、S3 时空回溯、S4 插件节点、L2 符号/调用边。

### 4.4 虚拟宠物（F-15 详述）

**定位**：纯情感陪伴，不影响任何功能能力，不与 agent 能力挂钩。可整体开关。

**机制设计**：
- **单只宠物**：每个用户一只，长期养成。
- **等级系统**：随用户使用时长增长，宠物等级提升；等级纯粹解锁外观/形态变化，不影响 agent 功能。
- **Agent 状态映射**：宠物的表情、动作、台词反映 agent 当前状态（如：思考中 / 执行工具中 / 完成 / 出错），作为状态的可视化提示，但不改变 agent 行为。
- **外观来源**：提供一只默认宠物；支持用户上传自定义外观。
- **对话陪伴**：宠物作为与用户对话/需求的存在感载体（具体呈现形式待定，不取代 F-01 的主对话流）。
- **桌面渲染**：以置顶透明无边框窗口悬浮于桌面其他窗口之上（类似桌面宠物）。
- **开关**：宠物功能支持整体开关；关闭后完全不加载、不占用资源。

**优先级**：P1（MVP-2 之后第一批迭代）。MVP-1/MVP-2 均不实现宠物，但架构需确保宠物可作为独立可选模块加载/卸载。

## 5. 非功能需求

| 编号 | 需求 | 说明 |
|:---|:---|:---|
| NF-01 | 跨平台 | Windows / macOS / Linux 桌面端同步支持。 |
| NF-02 | 轻量多开 | 支持同时开多个项目，每个项目一个窗口；多开时共享全局配置与 provider 进程/模型连接等运行时资源，尽量降低占用；项目配置隔离；同一项目开多个客户端时需共享同步文件状态。 |
| NF-03 | 性能 | UI 零延迟响应；核心编辑/对话流程不被渲染或动画阻塞；3D 首页受 G7 门约束（2k 节点 60fps，退化梯见 §4.2）。 |
| NF-04 | 可维护性 | 模块边界清晰，每个子系统可独立测试；支持无渲染的 headless 运行与消息流录制/回放。 |
| NF-05 | 国际化 | 从一开始就考虑国际化（i18n）架构，所有用户可见字符串走 i18n；前期以中文为主。 |
| NF-06 | 可扩展 | TUI / Web / 3D / 自定义工具 / MCP 的接入点在架构上预留，不因当前不实现而阻塞未来扩展。 |

## 6. 关键约束

1. **宠物纯情感向**：虚拟宠物（F-15）不影响任何功能能力，等级仅解锁外观，不改变 agent 行为。宠物功能支持开关，关闭后不占用资源。
2. **共享运行时降占用**：GUI 多开时，provider 进程/模型连接等运行时资源需共享，避免每窗口独立占用。
3. **Web 接口预留**：provider / tools / 文件访问等需走抽象层，使 Web 端（受 WASM 限制无法直接本地文件/子进程）将来可注入不同实现。当前不实现 Web，但架构不得与 Web 形态冲突。
4. **3D 是默认首页，不是可选插件层**：3D 可视化（F-16）进入 MVP-2 主线；必须保留 2D fallback 与 G7 性能退化梯（见 §4.2）。3D 数据层（`xgent_spatial`）不依赖 Bevy，视口在 `xgent_ui`。
5. **TUI 架构留口**：前期仅 GUI，TUI 不实现；核心逻辑与 UI 前端解耦，使未来 TUI 作为同一套核心的另一套前端实现，且不影响当前性能。
6. **沿用项目名**：继续使用 XGent，待有更合适名称再更名。
7. **参考成熟项目实现**：对于项目上下文检索（F-05）等需深入设计的功能点，需参考成熟项目实现后再定策略，不闭门造车。
8. **3D 性能先验证后铺开**：G7 spike 未通过前不做布局反转；2k 不达标走 800 节点/关特效的退化梯，仍不达标则由 2D 首页兜底。

## 7. 分期路线

### 7.1 MVP-1（已交付）

目标：一个真正能日常使用的 2D AI code agent GUI 桌面应用。

范围：F-01 ~ F-09 + NF-01/02/03/04。已提前交付：F-11 内置编辑器、F-19 内置终端（原 P1）。

**不含**：3D、宠物、TUI、Web、Git、成本统计、MCP、自定义工具。

### 7.2 MVP-2（3D 首页，首期已交付）

目标：把 README 的第一支柱落成默认形态——3D 代码宇宙成为首页，编辑器/终端打开时接管主区，对话常驻右栏。

范围：F-16（§4.2）。

**门槛与验收（细则以 §4.2 为准）**：

1. G7 性能 spike：2k 节点 60fps → 800 节点/关特效 60fps → 2D fallback。
2. S1 + 点击打开：渲染、轨道相机、悬停高亮、点击选中、双击/Enter 打开文件、Esc 回宇宙；所有操作有键盘路径。
3. L1 文件/目录图：任意项目打开都有宇宙；扫描忽略 `.gitignore`/`target`/`node_modules`；有 `Cargo.toml` 才叠 crate 依赖边。
4. 布局反转：3D 占 `Slot::Center`；对话右栏常驻；编辑器/终端接管主区；2D/3D 随时切换、不重启；关掉 3D 后 MVP-1 全部功能可用。

**不含**：完整 S2、S3 时空回溯、S4 插件节点、L2 符号/调用边。

### 7.3 第一批迭代（P1，3D 首页交付后）

P1 集合（顺序在 MVP-2 收尾时按依赖与价值排）：

- F-20 时空回溯（依赖 3D S3 与 D-3D-07；复用 F-03 的检查点）
- F-21 代码智能管线（符号/import/调用边；为 3D 虫洞与 F-05 检索 C 提供数据）
- F-12 成本统计

## 9. 开放问题

以下点已初步决策但实现细节待后续评估，不阻塞本需求文档定稿：

- **OQ-05**：宠物“对话陪伴”（F-15）的具体呈现形式——宠物气泡？独立面板？不取代主对话流的边界在哪。当前仍不确定，留待 P1 阶段设计时再定。
- **OQ-07**：会话持久化形态——本地文件、格式、是否跨项目。留待实现时考虑评估。
- **OQ-10**：成本统计（F-12）的数据来源与展示形态。留待实现时考虑。
- **OQ-11**：3D 首页首次启动是否让用户选 2D/3D？当前默认 3D，但保留偏好开关；引导形式待 MVP-2 设计。
- **OQ-12**：L1 节点聚合阈值（目录簇 vs 文件星）与 2k 节点上限的映射；L1 扫描的忽略规则（`.gitignore`/`target`/`node_modules`）在 S1 规格中定。与 `docs/design/ui-v8-3d-viewport.md` 的 D-3D 系列一起定。
- **OQ-13**：3D 自由飞行/惯性是否作为后续可选模式？MVP-2 用轨道相机、无惯性；自由飞行不在首期。

以下点已决策并落入正文，仅作记录：

- **OQ-01（已决策）**：支持 OpenAI / Anthropic / Ollama 等，及第三方兼容接口（OpenAI compatible）、新的响应式接口（如 Response API）、自定义 API。见 F-07。
- **OQ-02（已决策）**：内置编辑器为中等能力边界（多行+行号+undo/redo+查找+tree-sitter 高亮，仅 Rust）；基于 bevy_ui 自造（`xui::CodeEditor`，可独立发布），egui 混合方案作 P1+ 备选。完整能力边界（+LSP+split view）留后续。见 F-11 与 `docs/design/editor-design.md`。
- **OQ-03（已决策）**：快捷键参考 VSCode 体系。见 F-09。
- **OQ-04（已决策）**：默认一只宠物 + 用户上传自定义外观。见 §4.4。
- **OQ-06（已决策）**：共享全局配置，项目配置隔离；同一项目多客户端共享同步文件状态。见 NF-02。
- **OQ-08（已决策）**：采用演进式路径——MVP-1 与编辑器上线前用选项 1（A 无索引·按需读取 → B tree-sitter repo map）；**内置编辑器（F-11）上线触发到 C（向量 RAG）**，D（LSP/AST）**延后**到 LSP 真正接入时（即编辑器升完整边界），E（混合检索）跟随 D。分段理由：中等边界不含 LSP，D 依赖 LSP，解耦避免编辑器上线就硬依赖 LSP。索引层与 agent 之间走抽象接口，未来 Web 端可注入不同实现。详见 `docs/notes/context-retrieval-research.md` 与 `docs/decisions/0010-oq08-检索升级路径分段-编辑器到c-d延后.md`。
- **OQ-09（已决策）**：国际化从一开始就考虑。见 NF-05。
